# 随心一听变更与日志规范

## 1. 文档流

```text
用户反馈/新想法
  -> REQUIREMENTS.md（需求 ID / 状态 / 验收）
  -> BUG_CATALOG.md（若是缺陷）
  -> docs/bugfixes/<version>.md（本版本范围）
  -> 代码与构建
  -> QA_REGRESSION.md 对应 Test ID
  -> DEVELOPMENT_LOG.md（实际操作和结果）
  -> BUGFIX_LOG.md / GitHub Release
```

聊天记录不是单一事实来源。对话中的决定必须进入上述文档后才算项目基线。

## 2. 开发日志

`DEVELOPMENT_LOG.md` 采用追加式记录。每个版本包含：

```markdown
## x.y.z - 版本主题

### 需求范围
- REQ ID：目标与不包含内容。

### 操作记录
- YYYY-MM-DD HH:mm：实际执行的分析、修改、构建、安装和命令结果。

### Bug 与修复
- BUG ID：根因、代码落点、为何不会破坏旧行为。

### 验证
- Test ID：PASS/FAIL，证据路径和关键数值。

### 制品
- APK：
- SHA-256：
- Git commit：
- 回滚版本：

### 已知限制
- 未完成项、原因和下一步。
```

规则：

- 只记录实际发生的动作，计划写到版本文档，不伪装成完成。
- 失败命令保留简短结论和纠正动作。
- 日志时间使用 Asia/Shanghai。
- 不写 Cookie、token、签名口令、完整临时播放 URL。

## 3. 需求变更

- 新需求分配类别前缀和编号，如 `PLAY-011`。
- 需求范围改变时修改原条目并在日志写变更原因，不创建含义重复的新条目。
- “暂时不管”“后续做”对应 `暂缓` 或 `待开发`，不能删除。
- 用户明确降低优先级时保留需求并更新优先级。
- 完成状态必须满足项目手册的 Definition of Done。

## 4. Bug 生命周期

```text
新建 -> 可复现 -> 已定位 -> 已实现 -> 已验证 -> 已修复
                 \-> 环境问题 / 观察中 / 暂缓
```

- 复现和根因是不同阶段。
- 真机未验证时最多标记“已实现”。
- 修复后复发沿用原 ID。
- 每个已修复 Bug 至少关联一个 QA Test ID。

## 5. 版本修复文档

新文件 `docs/bugfixes/<version>.md` 使用模板：

```markdown
# <version> - 标题

## 需求
- REQ ID：

## 问题与根因
- BUG ID / 现象：
- 根因证据：

## 实现
- 文件/模块：
- 数据或兼容性影响：

## 测试计划
- [ ] Test ID：场景

## 验证结果
- 环境：
- 结果与证据：

## 制品与回滚
- APK / SHA-256：
- 上一稳定版：
```

## 6. 决策记录

影响长期架构的决定写入项目手册或架构文档，至少包括：

- 决定内容和日期。
- 考虑过的方案。
- 选择理由和代价。
- 触发重新评估的条件。

当前稳定决定：

2. 元数据同步、音频按需播放。

4. STREAM_MUSIC 是唯一用户音量。
5. 源音质和耳机 Codec 分层展示。

## 7. 文档审查清单

- [ ] 新需求/反馈已进入需求基线。
- [ ] 新 Bug 有 ID、复现、根因和状态。
- [ ] 新模块/数据流更新架构文档。
- [ ] 新工具或命令更新开发指南。
- [ ] 新回归场景更新 QA 矩阵。
- [ ] 版本号、APK、SHA 和验证结果一致。
- [ ] `docs/INDEX.md` 链接可达。
- [ ] 公开内容通过敏感信息扫描。
